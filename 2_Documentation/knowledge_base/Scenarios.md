## Зачем это вообще

Нужно уметь ответить на два вопроса:

1. Система жива? (сервисы отвечают на запросы?)
2. А вообще мы поступаем правильно? (JSON такой, какой ожидаем мы с тестами?)

В конкретно данном случае у нас должна быть пусть и небольшая, но выборка ответов должна навести на мысль, а вообще мы действуем правильно.

# Общие сценарии

## Сценарий 1: Сервис Cortex запущен

| Что сделать                    | Что должно получиться | Зачем                               |
| ------------------------------ | --------------------- | ----------------------------------- |
| Открыть `GET /health` у Cortex | Ответ  `status: ok`   | Убедиться, что API вообще доступен. |

Это самая первая проверка: если здесь пусто - дальше идти смысла нет, система не работает.

В идеальном и правильном сценарии мы должны получить следующий JSON ответ.

```json
{
  "status": "ok"
}
```

## Сценарий 2: Ollama настроена и доступна

| Что сделать                 | Что должно получиться                                      | Зачем                                                                                                                              |
| --------------------------- | ---------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------- |
| Открыть `GET /api/v1/ready` | В ответе видно, задан ли адрес Ollama и достигается ли она | Это позволяет определить ситуацию, что сам модуль мозга работает, а вот модель не отвечает и другие вытекающие из этого следствия. |

В нашем случае нам надо понимать, работаем ли мы в ограниченном режиме. 

В идеальном и правильном сценарии мы должны получить следующий JSON ответ.

```json
{
  "status": "ok",
  "ollama_configured": true,
  "ollama_reachable": true
}
```

## Сценарий 3: Правильный JSON без нейросети

| Что сделать                                                                   | Что должно получиться | Зачем                                                 |
| ----------------------------------------------------------------------------- | --------------------- | ----------------------------------------------------- |
| Вызвать `POST /api/v1/smoke/analyze` с нужным заголовком авторизации (Bearer) | Готовый JSON ответ    | Проверить только формат и корректную доставку данных. |
В нашем понимании это должен быть “эталонный бланк”. Если будет отличаться структура от того, что ожидаем, значит сломали API, а не плохо придумала модель. В данном случае проверяется чисто Supervisor на наличие каких-либо дефектов, которые нас не устраивают.

Ожидаемый JSON для данного сценария:

```json
{
  "incident_id": "smoke-analyze-1",
  "diagnosis": {
    "homeostasis_state": "NORMAL",
    "incident_class": "smoke_test",
    "primary_symptom": "REST and tunnel connectivity check",
    "scope": "cortex",
    "target_id": "smoke"
  },
  "confidence": "high",
  "actions": [
    {
      "type": "PAUSE_NEW_SESSIONS",
      "target": "smoke-target",
      "parameters": {},
      "expected_effect": "No production effect — smoke test only",
      "rollback": {
        "type": "RESUME_SESSIONS",
        "target": "smoke-target",
        "parameters": {},
        "expected_effect": "Revert smoke placeholder",
        "rollback": null
      }
    }
  ],
  "success_criteria": {
    "metric": "smoke.ok",
    "condition": "== 1",
    "window_seconds": 60
  },
  "requires_escalation": false,
  "escalation_reason": "",
  "reasoning": "Smoke test: this response was generated without calling the LLM. Use this endpoint to verify Cloudflare Tunnel, Bearer auth, and JSON shape."
}
```

# Игровые сценарии
### Сценарий 1: Лаг во время волны
История. 
	Как оператор платформы, я хочу, чтобы при просадке TPS и росте MSPT во время активной волны Mob Arena система сначала смягчила нагрузку, а не сразу рубила арену.
Игровой смысл
	Слишком много сущностей / тяжёлая логика - игроки видят лаг, волна ещё идёт.
Контракт
	Cortex предлагает не более трёх действий, в порядке от менее разрушительного: Сначала попробовать `REDUCE_MOB_COUNT` → при необходимости `INCREASE_WAVE_INTERVAL` и/или `SIMPLIFY_AI`; 
	В случае успешного исправления ситуации выполнить `RESTORE_MOB_COUNT`, `DECREASE_WAVE_INTERVAL`, `RESTORE_AI`.

### Сценарий 2: Волна залипла, прогресс не идёт
История
	Как система самовосстановления, я хочу аккуратно завершить проблемную сессию, если волна/арена в тупике, чтобы не копить нагрузку.
Игровой смысл
	Игроки застряли, таймеры/состояние арены неконсистентны.
Сигналы
	Рост `arena_soft_fail_total` или алерт про зависание волны, аномалия  длительности сессии при плохих TPS/MSPT.
Контракт
	Основное действие - `SOFT_FAIL_ARENA` (или, по политике документации, `RESTART_ARENA` как более жёсткий шаг). Откат - `RESTORE_ARENA` или возврат к допустимому состоянию через `RESUME_SESSIONS`, если явно описано это в ранбуке.

### Сценарий 3: Весь узел перегружен, новые сессии усугубляют
История
	Как платформа, я хочу временно не пускать новые арены, пока текущие не стабилизируются.
Игровой смысл
	Очередь в лобби, но сервер уже на пределе.
Сигналы
	Высокая `arena_sessions_active`, высокий `arena_players_in_arenas`, плохие TPS/MSPT, возможно рост `arena_incident_raised_total`.
Контракт
	`PAUSE_NEW_SESSIONS` с дальнейшим исполнением `RESUME_SESSIONS`; при необходимости плюс одно смягчающее действие из сценария 1 (например `REDUCE_MOB_COUNT` на уже идущих аренах), если метрики это поддерживают.

### Сценарий 4: Сложность завышена, игроки массово проигрывают / тайминги срываются
История
	Как баланс в режиме инцидента, я хочу временно ограничить сложность, не ломая сессию целиком.
Сигналы
	Из алертов/логов/метрик, согласованных с вашей документацией (например, рост ошибок, отмена волн, ваши `arena_*` счётчики).
Контракт
	`CAP_DIFFICULTY` + `RESTORE_DIFFICULTY` в rollback; при сопутствующем лаге — комбинация с A в пределах лимита в три действия.

### Сценарий 5: После жёсткого вмешательства нужно вернуть нормальный режим
История
	Как оператор, я хочу, чтобы после `RESTART_ARENA` или аналога система явно планировала восстановление и критерий успеха.
Контракт
	Действие `RESTART_ARENA` (или уже выполненное вне Cortex) → в плане отката/следующих шагов — `RESTORE_ARENA` там, где это имеет смысл в вашем runbook; критерий успеха в JSON — метрика вроде «TPS выше порога N секунд» (как в тестовом ранбуке RB-ARENA-LAG: MSPT < 40 за 120 с).

### Сценарий 6: Недостаточно данных / противоречивые метрики
История
	Как владелец безопасности автоматики, я хочу, чтобы Cortex не выдавал план действий, если контекст пустой или противоречивый.
Контракт
	Необходимо вызвать инженера через `requires_escalation: true`, заполненный `escalation_reason`, `actions` пустой или минимальный, установить `confidence: low` при необходимости. В таком случае Supervisor по коду не пойдёт в автоматическое исправление.
