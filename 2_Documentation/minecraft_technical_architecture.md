## 1. Назначение документа

Данный документ описывает **концептуальную техническую архитектуру** системы мини-игры *Minecraft Mob Arena*.

Цель документа:
- определить основные компоненты системы;
- зафиксировать их зоны ответственности;
- описать взаимодействие между компонентами;
- создать архитектурный каркас, пригодный для последующей реализации.

Документ **намеренно не содержит** привязки к конкретным API, платформам или библиотекам.

## 2. Архитектурный стиль

Система построена в соответствии со следующими принципами:

- **Сессионно-ориентированная архитектура** — каждая арена является изолированной сессией;
- **Event-driven взаимодействие** — компоненты обмениваются событиями, а не прямыми вызовами;
- **Изоляция доменов** — сбой в одном домене не распространяется на другие;
- **Self-healing по умолчанию** — восстановление является частью нормального поведения системы.

## 4. Основные компоненты

### 4.1 Lobby Layer (Velocity Proxy)

**Ответственность:**
- приём игроков;
- отображение доступных арен;
- формирование команд;
- изоляция от состояния арен.

**Ключевые свойства:**
- минимальная логика;
- высокая устойчивость;
- отсутствие зависимости от состояния игровых сессий.

### 4.2 Arena Management Layer (Velocity + Paper)

**Ответственность:**
- создание и завершение арен;
- распределение ресурсов;
- контроль количества активных сессий;
- инициирование soft-fail.

**Ключевые свойства:**
- централизованное управление;
- отсутствие игровой логики;
- принятие решений на основе мониторинга.

### 4.3 Arena Session (Paper)

**Ответственность:**
- управление жизненным циклом сессии;
- расчёт волн;
- спавн мобов;
- фиксация прогресса;
- локальное самовосстановление.

**Ключевые свойства:**
- изолированное состояние;
- ограниченные ресурсы;
- автономность.

### 4.4 Game Logic Module (Java Service)

**Ответственность:**
- формулы сложности;
- правила боя;
- расчёт наград;
- валидация игровых событий.

**Ключевые свойства:**
- детерминированность;
- параметризуемость;
- возможность упрощения.

### 4.5 Monitoring & Health Layer (LangFuse + Python + Java)

**Ответственность:**
- сбор метрик;
- определение состояния гомеостаза;
- генерация сигналов деградации;
- передача данных оператору.

**Ключевые свойства:**
- пассивное наблюдение;
- отсутствие влияния на игровой процесс напрямую;
- обязательная надёжность.

## 5. Взаимодействие компонентов

### 5.1 Событийная модель

Компоненты взаимодействуют через события:
- `ArenaCreatedEvent`
- `ArenaDestroyedEvent`
- `WaveStartedEvent`
- `WaveCompletedEvent`
- `DegradationTriggeredEvent`
- `SoftFailInitiatedEvent`
- `SessionStartedEvent`
- `SessionEndedEvent`

Прямые вызовы между доменами запрещены.

### 5.2 Потоки данных

- игровые события → Monitoring Layer;
- сигналы деградации → Arena Management;
- команды стабилизации → Arena Session.

## 6. Границы ответственности

| Компонент        | Не отвечает за          |
| ---------------- | ----------------------- |
| Lobby            | Производительность арен |
| Arena Management | Игровую логику          |
| Arena Session    | Состояние сервера       |
| Game Logic       | Мониторинг              |
| Monitoring       | Управление аренами      |

## 7. Ошибки и отказоустойчивость

### 7.1 Локализация ошибок
- ошибки в Arena Session не должны влиять на другие сессии;
- сбои логики не должны ломать управление аренами.

### 7.2 Стратегия отказа
- локальный restart сессии;
- soft-fail при невозможности восстановления;
- уведомление оператора.

## 8. Ограничения архитектуры
- архитектура приоритетно оптимизирована под устойчивость, а не максимальную производительность;
- сложность ограничивается сверху сознательно;
- расширение системы требует пересмотра инсайтов.

## 9. Итоговые положения
- Архитектура поддерживает параллельные арены.
- Каждый компонент имеет чёткую ответственность.
- Self-healing встроен в архитектурный каркас.
