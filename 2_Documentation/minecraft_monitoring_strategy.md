## 1. Назначение документа

Данный документ описывает **стратегию мониторинга** системы мини-игры *Minecraft Mob Arena*.

Мониторинг рассматривается как **активный компонент архитектуры**, обеспечивающий:
- обнаружение отклонений от гомеостаза;
- раннее выявление деградации;
- автоматические триггеры самовосстановления;
- минимизацию пользовательского ущерба.

Ключевой принцип:
> *Если состояние системы нельзя измерить - оно не может считаться контролируемым.*

## 2. Роль мониторинга в системе

Мониторинг выполняет следующие функции:
- трансляция абстрактных состояний гомеостаза в измеримые сигналы;
- обеспечение входных данных для self-healing механизмов;
- поддержка оператора при принятии решений;
- фиксация фактов для последующего анализа и улучшения системы.

Мониторинг **не является логированием** и не предназначен для отладки кода.

## 3. Уровни мониторинга

### 3.1 Уровень сервера

Отражает общее состояние вычислительных ресурсов.

**Ключевые сигналы:**
- TPS (Ticks Per Second, игровых тактов в секунду)
- MSPT (Milliseconds Per Tick, количество времени затраченное на игровую логику за единицу игрового такта)
- использование памяти
- частота сборок мусора

### 3.2 Уровень арен

Отражает состояние отдельных игровых сессий.

**Ключевые сигналы:**
- количество активных арен
- средняя длительность волн
- количество активных сущностей
- частота рестартов арен

### 3.3 Уровень игрового процесса

Отражает качество игрового опыта.

**Ключевые сигналы:**
- время реакции мобов
- задержка старта волн
- количество аномальных смертей игроков

## 4. Связь метрик с состояниями гомеостаза

| Метрика       | HEALTHY     | DEGRADED          | CRITICAL     | FAILED            |
| ------------- | ----------- | ----------------- | ------------ | ----------------- |
| TPS           | ~20.00      | 15.00-19.99       | <15.00       | Недоступен        |
| MSPT          | <40.00      | >40.00, но <62.50 | >62.50       | Недоступен        |
| Задержка волн | Отсутствует | Незначительная    | Значительная | Волны не стартуют |
| Ошибки        | Редкие      | Умеренные         | Массовые     | Постоянные        |

## 5. Триггеры деградации

### 5.1 Переход HEALTHY → DEGRADED

Возможные условия:
- устойчивое повышение MSPT;
- рост задержек игровых событий;
- увеличение нагрузки от сущностей.

**Реакция:**
- упрощение ИИ мобов;
- снижение плотности мобов;
- увеличение интервалов между волнами.

### 5.2 Переход DEGRADED → CRITICAL

Возможные условия:
- резкое падение TPS;
- рост ошибок;
- нестабильность арен.

**Реакция:**
- остановка новых сессий;
- агрессивное упрощение логики;
- подготовка soft-fail.

### 5.3 Переход CRITICAL → FAILED

Возможные условия:
- невозможность стабилизации;
- повторяющиеся фатальные ошибки.

**Реакция:**
- корректное завершение активных арен;
- сохранение прогресса;
- переход в режим восстановления.

## 6. Мониторинг пользовательского ущерба

### 6.1 Аномальные смерти игроков

Смерти, не объяснимые игровой логикой, считаются сигналом критического дефекта.

**Примеры сигналов:**
- смерть без входящего урона;
- телепортация моба перед ударом;
- резкое падение здоровья.

### 6.2 Потеря прогресса

Любая потеря зафиксированного прогресса считается критическим инцидентом.

## 7. Взаимодействие с оператором

Мониторинг обязан:
- предоставлять агрегированные сигналы, а не шум;
- минимизировать ложные срабатывания;
- чётко указывать текущее состояние системы.

Оператор должен видеть:
- текущее состояние (HEALTHY / DEGRADED / CRITICAL / FAILED);
- причину перехода;
- предпринятые автоматические действия.

## 8. Ограничения стратегии мониторинга

- Мониторинг не гарантирует предотвращение всех отказов;
- Мониторинг не заменяет корректную архитектуру;
- Чрезмерный мониторинг увеличивает сложность системы.

## 9. Итоговые положения

- Стратегия мониторинга неразрывно связана с гомеостазом.
- Все self-healing действия должны быть инициированы измеримыми сигналами.
- Отсутствие метрики для критического состояния является архитектурной ошибкой.–
