#### `arena-lobby-gateway`  (Paper)

**Задача:** тонкий “входной шлюз” для игроков.

- Команды/GUI: выбор режима/карты/сложности, “войти в очередь”.
- Валидации доступа: права LuckPerms (группы, лимиты, приоритеты).
- Перенаправление на Paper-арену по решению matchmaker’а.
- Минимальный state: только “куда игрок хочет” и “куда его направить”.

Реальные показатели живут на Paper. На Velocity мы их лишь агрегируем.

## 1. Общие сведения

**`arena-lobby-gateway`** - плагин Paper, реализующий единый **UX + Access** вход в матчмейкинг: команды/GUI, проверка прав LuckPerms, формирование “намерения игрока”, отправку в `arena-matchmaker` и безопасное перенаправление игрока на целевую арену.

Плагин обеспечивает **предсказуемую, минималистичную и отказоустойчивую** постановку игрока в очередь, не владея игровой логикой и не держа тяжёлое состояние арен.
## 2. Границы ответственности

### `arena-lobby-gateway` отвечает за
1. **UI входа**: команды и GUI выбора.
2. **Валидации доступа** через LuckPerms: права, группы, приоритеты (и опционально лимиты, если включены).
3. **Формирование join intent** (минимальный контракт “куда хочу”) и отправку в matchmaker.
4. **Отображение статуса** игроку: queued/assigned/rejected/error.
5. **Перенаправление** игрока на арену по решению matchmaker (соединение на прокси-цель).
6. **Минимальный state** игрока в лобби: intent + статус + target (если назначен) + TTL.
### `arena-lobby-gateway` НЕ отвечает за

1. Матчмейкинг-логику: выбор арены/балансировку/очереди как систему (это `arena-matchmaker`).
2. Управление аренами/мирами/WE/WG/схематиками/сбросом (это `arena-world-manager` на аренах).
3. Игровую сессию, волны, мобов, награды, результаты (это `arena-runtime`).
4. Health/инциденты/обнаружение типовых отказов на Paper (это `arena-observability`; gateway - только лёгкие UX-метрики и события входа).
5. Любые кросс-мирные/кросс-аренные операции (шлюз не трогает мир и регионы).
## 3. Архитектурные принципы и инварианты
### Тонкий шлюз (Thin Gateway)
- Любая логика, не относящаяся к **входу/валидации/контракту/перенаправлению**, запрещена.
- Нельзя “обрастать” логикой арен: шлюз должен оставаться независимым от runtime/world-manager.
### Надёжность > фичи
- При конфликте “богатый UI” vs “предсказуемость и отсутствие зависаний” выбирается стабильность.
- Неизвестный/битый ответ matchmaker трактуется как безопасный отказ.
### Минимальный state и TTL
- Любое состояние игрока имеет TTL и обязано корректно очищаться на дисконнекте/таймауте.
- Нельзя хранить состояние “очереди” локально как источник истины.
### Event-driven / контрактное взаимодействие
- Взаимодействие с matchmaker - строго по контракту request/response, без “договорённостей на словах”.
- Версионирование контракта предусмотрено с первого дня (см. раздел 7).

## 4. Жизненный цикл “заявки игрока” (FSM)
### Состояния (Player Intent FSM)
1. **IDLE** - у игрока нет активной заявки.
2. **SELECTING** - игрок выбирает параметры в GUI.
3. **QUEUED** - intent отправлен, matchmaker подтвердил постановку в очередь или ожидание назначения.
4. **ASSIGNED** - matchmaker назначил цель (`targetServerId`), шлюз готовит трансфер.
5. **TRANSFERRING** - выполняется перенаправление (connect).
6. **FAILED** - ошибка (permission/timeout/reject/transfer_failed).
7. **CANCELLED** - игрок отменил заявку.

Состояния и переходы обязаны быть валидированы: нельзя прыгать в `TRANSFERRING` без `ASSIGNED`, нельзя держать `QUEUED` без актуального TTL.

### Переходы и условия
- `IDLE -> SELECTING`: открытие GUI.
- `SELECTING -> QUEUED`: успешная валидация + отправка join intent + ответ `QUEUED/ACCEPTED`.
- `QUEUED -> ASSIGNED`: получение `ACCEPTED`/назначения.
- `ASSIGNED -> TRANSFERRING`: инициирован connect на целевой сервер.
- `TRANSFERRING -> IDLE`: best-effort подтверждение (или пост-фактум очистка).
- Любое состояние -> `FAILED`: reject/timeout/ошибка транспорта/ошибка LuckPerms.
- `QUEUED/FAILED/ASSIGNED -> CANCELLED`: `/arena leave` или отмена в UI.
### Таймауты (чтобы не “зависать” навечно)
- `MATCHMAKER_REQUEST_TIMEOUT` (например 1–3с) → `FAILED(timeout)`.
- `QUEUE_TTL` (например 2–5 мин) → `FAILED(expired)` + авто-сброс в `IDLE`.
- `TRANSFER_TIMEOUT` (например 5–10с best-effort) → `FAILED(transfer_failed)` + кнопка “Повторить”.

## 5. UI/Команды/Поведение игрока

### Команды (минимально обязательные)

- `/arena` - открыть главное меню.
- `/arena join [map]` - быстрый вход без GUI.
- `/arena leave` - отмена заявки/выход из очереди.
- `/arena status` - текущий статус заявки.
- `/arena reload` - админ (перезагрузка конфигов).
- `/arena debug <player>` - админ (диагностика state/последнего ответа).

Требования:
- Все команды должны быть безопасны при повторном вызове (идемпотентны на уровне результата).
- Любые некорректные аргументы → help + список допустимых значений из конфигурации.

### GUI (обязательный минимум)

Функции:
- Выбор **карты** (или “Любая”).
- Кнопка **“Войти в очередь”**.
- Экран статуса: `В очереди / Назначено / Перенаправление / Ошибка`.

Надёжность UX:
- Защита от спама кликов (см. 9, rate limit).
- Любая ошибка → понятное сообщение, без “мертвого” GUI.

## 6. Валидации доступа (LuckPerms)

### Принцип deny-by-default
Если LuckPerms недоступен/ошибка API - **запрос отклоняется**, игроку показывается корректное сообщение, в лог - ERROR.
### Требуемые проверки
1. **Доступ к режиму**: `arena.join.<mode>`.
2. **Доступ к сложности**: `arena.join.<mode>.<difficulty>` (или иной шаблон из конфигов).
3. **Приоритет**: определение `priorityTier` по пермишенам (например `arena.queue.priority.vip`) и маппинг в число.
4. **Лимиты** (опционально, если включено):
    - антиспам join;
    - лимит одновременных заявок на игрока (строго 1);
    - дополнительные лимиты (если решишь реализовывать на gateway, но по умолчанию лучше оставлять на matchmaker).

### Результат валидации
- Игрок получает короткую причину (без технических деталей).
- В лог идёт `ACCESS_DENIED` с кодом причины и узлом permission.

## 7. Интеграции и контракты (API / Events)
## Взаимодействие с `arena-matchmaker` (Velocity)

Шлюз обязан реализовать контракт **request/response**.
### Transport
- Сообщения плагинов через прокси.
- Все операции асинхронны, с таймаутом.

### Join Intent (Request)

Обязательные поля:
- `contractVersion`
- `requestId` (UUID)
- `playerUuid`, `playerName`
-  `mapPreference?`
- `priority` (число)
- `timestamp`

### Response (от matchmaker)
Варианты:
- `QUEUED` + `queuePosition?` + `estimatedWaitMs?`
- `ACCEPTED` + `targetServerId` (+ `targetHint?`)
- `REJECTED` + `reasonCode` + `messageKey?`
- `CANCELLED/EXPIRED`

Правила обработки:
- Любой неизвестный `reasonCode` → `FAILED(internal)`.
- Неполный `ACCEPTED` без `targetServerId` → `FAILED(protocol_violation)`.

## Взаимодействие с прокси (перенаправление)
Шлюз инициирует connect на `targetServerId` .
- До соединения фиксируется `ASSIGNED`.
- После соединения - очищение state.

## События домена 
Gateway эмитит события (для логов/метрик/возможного экспорта):
- `IntentCreated`
- `AccessDenied`
- `MatchmakerRequestSent/ResponseReceived`
- `TransferInitiated/TransferFailed`
- `IntentCancelled/IntentExpired`
## 8. Soft-Fail и отказоустойчивость

### Soft-Fail как штатный сценарий
Если что-то пошло не так (matchmaker недоступен, таймаут, протокол нарушен, перенос не удался), шлюз обязан:
- оставить игрока в лобби;
- очистить/перевести state в `FAILED`;
- показать понятную причину и действие “повторить/изменить выбор”.
### Типовые причины soft-fail
- `MATCHMAKER_TIMEOUT`
- `MATCHMAKER_UNAVAILABLE`
- `PROTOCOL_VIOLATION`
- `TRANSFER_FAILED`
- `LP_ERROR`

Главный запрет:
- Никаких киков/крашей потока игрока из-за внутренних ошибок шлюза.

## Нефункциональные требования

### Производительность
- Запрещены блокирующие сетевые операции в основном потоке.
- GUI/команды обязаны выполняться мгновенно; ожидание ответа - асинхронно.

### Надёжность
- Все операции на state игрока должны быть потокобезопасны (Paper main thread + async callback → строгая синхронизация/маршаллинг обратно на main).
- Повторный `/arena join` при активном `QUEUED/ASSIGNED` → либо “уже в очереди”, либо “сначала /arena leave”.
### Тестируемость
- Валидации, FSM, контракт сериализации/десериализации - вынести в чистые классы, чтобы тестить без сервера.
- Интеграционные тесты: имитация ответов matchmaker + проверка переходов FSM.

## 10. Конфигурация

### Основные параметры
- Список `modes` и доступных `difficulties`.
- `maps` (enable/disable, отображаемые имена).
- Permission-шаблоны:
    - `permJoinModePattern`
    - `permJoinDifficultyPattern`
    - `priorityTiers` (tier → numeric priority)
- Таймауты:
    - `matchmakerTimeoutMs`
    - `queueTtlMs`
    - `transferTimeoutMs`
- Rate limits:
    - `perPlayerJoinBurst`
    - `globalJoinRps`
    - `cooldownMs`
- UI:
    - тексты, локализация, оформление GUI.

### Версии конфигов
- `configVersion` обязателен.
- При несовместимости: безопасный отказ запуска функций (join), понятный лог + сообщение админу.
## 11. Логирование и диагностика

### Структурные логи
- `JOIN_INTENT_CREATED {requestId, playerUuid, mode, difficulty, mapPreference, priority}`
- `ACCESS_DENIED {playerUuid, reason, permNode}`
- `MM_REQUEST_SENT {requestId}`
- `MM_RESPONSE_RECEIVED {requestId, outcome, latencyMs}`
- `TRANSFER_INITIATED {playerUuid, targetServerId}`
- `TRANSFER_FAILED {playerUuid, targetServerId, reason}`
- `INTENT_EXPIRED/CANCELLED {playerUuid, requestId}`

### Диагностика
- `/arena debug` должен показывать:
    - state, requestId, mode/difficulty/mapPreference, lastError, timestamps
    - последнюю нормализованную “причину отказа”
## 12. Метрики
Да, основные метрики живут на арене, но gateway обязан дать минимум “что происходит на входе”:

- `lobby_gateway_join_requests_total`
- `lobby_gateway_join_denied_total{reason}`
- `lobby_gateway_matchmaker_latency_ms` 
- `lobby_gateway_transfers_total{result}`
- `lobby_gateway_queue_active` 

Этого достаточно, чтобы видеть всплески отказов, деградацию matchmaker и проблемы трансфера, не превращая плагин в observability.

## 13. Требования к безопасности игрового опыта
Критическое требование для шлюза:
- Игрок **не должен** попадать в “полумир” (частично перенесён / потерян / застрял).
- Любая ошибка → игрок остаётся в лобби, получает понятный статус, может повторить действие.

Практически это означает:
- строгая идемпотентность операций state;
- на одного игрока только одна активная заявка;
- запрет на “тишину” (если нет ответа/ошибка - всегда сообщаем и логируем).
