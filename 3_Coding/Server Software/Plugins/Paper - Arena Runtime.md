#### `arena-runtime` (Paper)

**Задача:** ядро игровой сессии (одна арена = один рантайм/контекст).
- Управление жизненным цикла арены: `IDLE -> PREPARE -> RUNNING -> FINISH -> RESET`.
- Волны, спавн, трек прогресса, награды, таблицы результатов.
- Вся логика мини-игры и самой арены.
- Сильная изоляция: runtime арены не лезет “в соседние арены”.

Вся игровая механика, сущности, мир, регионы, спавн - это серверная часть и прямое взаимодействие с миром, а не только сетевая часть.

## 1. Общие сведения

**`arena-runtime`** - плагин Paper, реализующий ядро игровой сессии на арене: жизненный цикл арены, волны, спавн, прогресс, награды, таблицы результатов.

Плагин обеспечивает **детерминированное и изолированное** выполнение одной игровой сессии в пределах одной арены (один рантайм/контекст), без влияния на другие арены/сессии.

## 2. Границы ответственности (Scope & Out of Scope)

###  `arena-runtime` отвечает за

1. **Жизненный цикл арены**: `IDLE -> PREPARE -> RUNNING -> FINISH -> RESET`.
2. **Игровой цикл**: волны, условия старта/завершения, переходы между волнами.
3. **Спавн и управление сущностями боя** (мобы/объекты, относящиеся к сессии).
4. **Трекинг прогресса**: номер волны, очки/вклад игрока, накопленные награды (в рамках сессии).
5. **Награды и результаты**: расчёт и выдача (или подготовка к выдаче) по итогу.
6. **Таблица результатов**: сбор, форматирование, выдача в UI/чат/инвентарь-GUI.

###  `arena-runtime` НЕ отвечает за
1. Управление картами/схематиками/WorldEdit/WorldGuard регионами
2. Публикация метрик наружу/агрегация/health-snapshots/детекция типовых отказов
3. Матчмейкинг, очереди, выбор арены, сетевые решения
4. Прямые кросс-аренные вызовы/общие статические глобальные “менеджеры всего” без ключа арены (см. изоляцию).
## 3. Архитектурные принципы и инварианты

### Изоляция арен
- Любое состояние runtime **привязано к ArenaId** и не может читаться/писаться без явного контекста арены.
- Runtime не имеет права:
    - обращаться к сущностям/регионам/миру, не принадлежащим своей арене;
    - управлять игроками, не зарегистрированными в текущей сессии;
    - менять глобальные gamerules/серверные настройки, влияющие на другие арены.  
        Основание: предотвращение каскадных отказов.

### Надёжность > сложность
- При конфликте “крутая механика” vs “стабильность/предсказуемость” выбирается стабильность.
- Допускается деградация механик, но не допускается системная смерть игрока из-за багов/лагов.

### Event-driven взаимодействие
- Взаимодействия с другими модулями строятся через события/контракты, а не прямую логику управления аренами.

## 4. Жизненный цикл арены (FSM)
### Состояния
1. **IDLE** - арена свободна, нет активной сессии, нет активных боевых сущностей.
2. **PREPARE** - подготовка сессии (регистрация игроков, подготовка мира через `arena-world-manager`, телепорты, выдача старт-кита, инициализация прогресса).
3. **RUNNING** - активный бой, волны, спавн, трекинг.
4. **FINISH** - завершение сессии: подсчёт результатов, выдача наград, отображение итогов, подготовка к выходу игроков.
5. **RESET** - очистка арены, деспавн сущностей, запрос сброса мира `arena-world-manager`, возврат в `IDLE`.

Состояния и переходы должны быть строго валидированы (невозможны “прыжки” мимо обязательных стадий без аварийного сценария).
### Переходы и условия
- `IDLE -> PREPARE`: по команде запуска (внешний триггер), при наличии валидной конфигурации арены и списка игроков.
- `PREPARE -> RUNNING`: после успешной подготовки мира/регионов и телепортов.
- `RUNNING -> FINISH`: при поражении команды, добровольном выходе по правилам, достижении лимита волн (если задан), либо soft-fail.
- `FINISH -> RESET`: по истечении таймера показа результатов или после подтверждения завершения.
- `RESET -> IDLE`: после успешного очищения и подтверждения готовности арены.

User flow “каждую 5-ую волну — продолжить/уйти” обязателен как базовое поведение.
### Таймауты
Чтобы не зависать навечно:
- `PREPARE_TIMEOUT` (например, 30-60с): если мир/телепорты/регион не готовы → soft-fail/abort.
- `WAVE_TIMEOUT`: если волна “зависла” (условия завершения не достигаются) → аварийное завершение волны или soft-fail по политике.
- `FINISH_TIMEOUT`: авто-переход в `RESET`.
- `RESET_TIMEOUT`: если сброс мира не подтвердился → пометка арены как “непригодной” (через событие наружу) и блокировка повторного старта до ручного вмешательства человека.

Тихие отказы и зависшие волны - критичны, должны иметь управляемую развязку.

## 5. Игровая логика: волны и бой

### Базовый цикл волны

1. Начало волны  
2. Расчёт параметров 
3. Спавн игроков и монстров 
4. Бой 
5. Проверка команды 
6. Завершение волны.

### Требования к волнам

- Волна имеет уникальный `waveId` в рамках сессии (номер волны?).
- Волна имеет параметры: состав мобов, количество, модификаторы (скорость/здоровье/урон), время старта, время завершения.
- Для каждой волны должны быть определены:
    - критерии завершения (все мобы уничтожены / условие эвакуации / таймер / поражение);
    - допустимые исключения (например, “моб застрял в блоках” → принудительная зачистка).
### Ограничения сложности

Даже при “динамике” сложность должна иметь верхние границы, чтобы не убить сервер.
  
Требование заключается в том, что все формулы/настройки волны обязаны проходить через **валидатор лимитов** (макс. мобов, макс. модификаторы, макс. активных сущностей и т.п.).
### Деградация геймплея \
Runtime должен поддерживать режимы упрощения (по команде/флагу/внешнему сигналу):
- уменьшить количество мобов;
- увеличить интервал между волнами;
- отключить “тяжёлые” механики;
- упростить ИИ/путь (если применимо).  
    Основание: деградация - допустимый инструмент ради устойчивости.

> Важно: **решение о переходах HEALTHY/DEGRADED/CRITICAL** принимает не runtime, а контур мониторинга/управления. Runtime лишь исполняет допустимые команды/режимы.

## 6. Игроки, команды, прогресс, награды

### Регистрация игроков

- В PREPARE runtime фиксирует “состав сессии” (UUID игроков, роли/классы при наличии, стартовые параметры).
- В RUNNING обработка join/quit:
    - если игрок вышел добровольно по правилам (после каждой 5-й волны) → применить сценарий “эвакуации” и сохранить прогресс.
    - если игрок вылетел/дисконнект → политика задаётся конфигом (например, мягкий таймер на переподключение, затем считать выбывшим).
- Любые действия над игроком вне состава сессии запрещены.
### Прогресс
Минимальный набор:
- номер текущей волны;
- время в сессии;
- вклад игрока (урон/киллы/хил/ассист);
- накопленные награды (не обязательно сразу выдавать предметами).  
    Потеря прогресса считается критическим ущербом - при сбоях использовать soft-fail с максимально возможным сохранением.

### Награды
- Выдача наград должна быть **идемпотентной** (повторный вызов не удваивает награду).
- Рекомендуемая модель: расчёт в FINISH → запись с флагом `rewarded=false` → выдача → `rewarded=true`.
- При soft-fail: выдача “минимально честной” награды (по политике), но не “обнуление”.

### Таблица результатов
- Формируется в FINISH.
- Содержит: достигнутая волна, время, топ-вклад, причина завершения.
- Должна быть доступна для вывода игрокам и (опционально) для внешней системы (через событие).
## 7. Интеграции и контракты (API / Events)

### Внутреннее API (для других плагинов )
Runtime обязан предоставить **стабильный сервис-интерфейс** (Java API), не раскрывая внутренние структуры:

Примерный набор:
- `ArenaRuntimeManager`:
    - `startSession(ArenaId, SessionSpec) -> SessionId`
    - `requestStopSession(ArenaId, StopReason)`
    - `getState(ArenaId) -> ArenaState`
    - `getSnapshot(ArenaId) -> RuntimeSnapshot` (только чтение)
- `DegradationControl` (исполнение команд упрощения):
    - `applyProfile(ArenaId, DegradationProfile)`
    - `clearProfile(ArenaId)`

Прямые вызовы “извне” на сущности/волну запрещены (только через менеджер и контекст арены).
### События домена (Domain Events)
Runtime должен эмитить события (внутриплагинно):
- `SessionLifecycle`: started/prepared/running/finished/reset
- `WaveLifecycle`: wave_started/wave_completed/wave_failed
- `PlayerSession`: player_joined/left/evacuated/died
- `Rewards`: rewards_calculated/rewards_granted
- `SoftFail`: softfail_triggered (причина), softfail_completed

События нужны для мониторинга/объяснимости и последующего self-healing контура.
### Взаимодействие с `arena-world-manager`
- Runtime вызывает world-manager **только в PREPARE и RESET**, через явный контракт:
    - `prepareArena(ArenaId, MapSpec) -> PrepareResult`
    - `resetArena(ArenaId) -> ResetResult`
- Runtime не должен сам делать WorldEdit/WorldGuard операции.
## 8. Soft-Fail и отказоустойчивость
### Soft-Fail как штатный сценарий
При невозможности продолжать корректно, runtime обязан:
- остановить спавн/тяжёлые механики;
- зафиксировать доступный прогресс;
- корректно завершить сессию;
- вернуть игроков в безопасное состояние (через интеграцию/команду перехода в лобби — сама транспортировка может быть вне runtime, но runtime должен инициировать состояние “готов к возврату”).
### Причины soft-fail
- PREPARE_TIMEOUT (мир не подготовлен);
- невозможность заспавнить волну в пределах лимитов;
- критическая ошибка в обработчиках боя/волн;
- зависшая волна, которую нельзя корректно разрулить (по политике).

### Главный запрет
Soft-fail не должен создавать каскадный отказ других арен. Любые “глобальные перезапуски” запрещены на уровне runtime.
## 9. Нефункциональные требования

### Производительность
- Runtime не должен выполнять тяжёлые операции синхронно в основном потоке, если это можно разнести (генерация списков волн, подготовка наград и т.п.).
- В RUNNING запрещены:
    - бесконтрольные сканирования мира целиком;
    - “поиск всех сущностей на сервере” без фильтра арены;
    - синхронные длительные IO операции.

### Надёжность
- Все критические операции обязаны быть:
    - либо идемпотентными,
    - либо защищёнными от повторного вызова (guard-флаги/состояния).
- Любая ошибка в обработчиках не должна оставлять арену “между состояниями”; при исключении выполняется аварийная развязка (FINISH/RESET/soft-fail).

### Тестируемость
- Логика волн/прогресса должна быть максимально вынесена в чистые классы (POJO), чтобы тестировать без сервера.
- Интеграционные тесты: минимальный прогон FSM и волнового цикла на тестовой арене.

## 10. Конфигурация

### Конфиг арены
Для каждой арены должны задаваться:
- `arenaId`
- параметры мира/карты
- спавн-точки игроков и мобов
- лимиты: `maxMobsPerWave`, `maxActiveMobs`, `maxWave`, `timeouts`, `grace-periods`
- правила эвакуации “каждую 5-ю волну”: включено/выключено, окно времени выбора
- профили деградации (набор заранее выбранных значений)

### Версионирование конфигов
- Конфиги должны иметь `configVersion`.
- При несовместимости - отказ запуска сессии и понятное логгирование и диагностика.
## 12. Логирование и диагностика
- Runtime пишет структурные логи жизненного цикла: переход состояний, причины старта и остановки, soft-fail причины.
- Runtime **не публикует метрики**, но обязан формировать события, пригодные для `arena-observability`.

## 13. Требования к безопасности игрового опыта
Критическое требование проекта:
- Смерть игрока из-за багов/лагов/неконсистентного состояния - худший исход; система обязана предпочитать деградацию или soft-fail.

На практике для runtime это означает:
- строгая валидация спавна/урона/событий;
- защита от “двойных” обработчиков;
- невозможность появления мобов вне зоны арены (по данным карты/регионов).
